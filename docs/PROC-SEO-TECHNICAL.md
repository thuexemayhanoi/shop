# PROC-SEO-TECHNICAL — Technical SEO Audit

## Objective

Verify that the deployed site is technically crawlable and indexable:
HTTP status, indexability, robots, canonical, sitemap, internal links,
orphan pages, duplicate content signals, and post-build HTML integrity.
This procedure distinguishes SOURCE checks (files in the repo, pre-deploy)
from LIVE checks (the deployed GitHub Pages site) — they are never
interchangeable.

## Preconditions

- Fresh checkout of current MAIN (or a fresh tarball of it).
- `curl` available (all live commands below use curl only).
- Read `config/site.json` (base path `/shop`) and `robots.txt`.

## Canonical data sources

- `config/site.json` — site URL + base path.
- `robots.txt` (repo root, deployed verbatim).
- `sitemap.xml` — regenerated by the publish transaction; canonical list
  of PUBLISHED article URLs + legacy URLs + child hub URLs.
- `data/content-matrix.csv` — which articles SHOULD be public (PUBLISHED
  rows exactly).
- `node scripts/js/factory.mjs --consistency` output — the machine truth
  that sitemap/hubs/matrix agree.

## Steps

### A. Source-side checks (repo, pre-deploy) — verified commands

```bash
# 1. Matrix vs reality agreement (never bypassed; also runs in CI/operator flows)
node scripts/js/factory.mjs --consistency
# expect: CONSISTENCY OK: <N> production rows, <M> sitemap URLs, 6 hub block(s) current

# 2. Sitemap + hub generator freshness (python vs node byte-equality)
python3 scripts/generate_sitemap.py --check
python3 scripts/generate_category_pages.py --check

# 3. Full test suites
python3 -m unittest discover tests        # expect: Ran <n> tests / OK
node --test tests/js/factory.test.mjs    # expect: # fail 0

# 4. Placeholder/canonical sweep over generated pages (source-level)
grep -rl "example.com" cam-nang/ | wc -l        # expect 0
grep -rl 'rel="canonical"' cam-nang/ | wc -l    # expect == number of cam-nang pages
```

### B. Live checks (deployed site) — verified command patterns

```bash
U=https://thuexemayhanoi.github.io/shop

# 1. HTTP status of every PUBLISHED URL (expect 200 for all)
for u in $(curl -s $U/sitemap.xml | grep -o '<loc>[^<]*</loc>' | sed 's/<[^>]*>//g'); do
  code=$(curl -s -o /dev/null -w "%{http_code}" "$u"); echo "$code $u";
done | grep -v "^200" | wc -l    # expect 0

# 2. Indexability (expect no noindex anywhere)
for u in <sample or all sitemap URLs>; do curl -s "$u" | grep -c 'name="robots"[^>]*noindex'; done | grep -v "^0" | wc -l   # expect 0

# 3. Deploy-gate proof for any new article, BEFORE publish is verified:
curl -s -o /dev/null -w "%{http_code}" $U/_drafts/cam-nang/<cat>/<slug>.html   # expect 404 (Jekyll never deploys underscore dirs)
curl -s -o /dev/null -w "%{http_code}" $U/cam-nang/<cat>/<slug>.html          # expect 404 until published, 200 after

# 4. Byte-integrity (live == repo)
curl -s $U/cam-nang/<cat>/<slug>.html | md5sum   # compare with local md5sum

# 5. Sitemap reachability + count agreement with --consistency output
curl -s -o /dev/null -w "%{http_code}" $U/sitemap.xml   # expect 200
curl -s $U/sitemap.xml | grep -c "<loc>"               # must equal the --consistency sitemap count

# 6. robots.txt deployed as-is
curl -s $U/robots.txt   # must match repo robots.txt; Sitemap line points at $U/sitemap.xml
```

### C. Link / orphan / duplicate checks

- Broken internal links: the scorer FAILs any article with a broken
  required internal link (source-level, every QA run). Site-level: for a
  sample of live pages, extract internal hrefs and curl each (expect 200).
  No automated site-wide link crawler exists — see TODOs.
- Orphan pages: every PUBLISHED article must appear on its parent category
  hub (first 50) or a hub pagination page, and on its child topic hub.
  `--consistency` verifies hub blocks are current; child hubs list only
  PUBLISHED articles. An article in the sitemap but on NO hub = defect.
- Duplicate content: exact-duplicate titles across articles are critical
  FAILs in the scorer; near-similar titles (≥0.90 similarity) are REVIEW
  flags. Site-wide duplicate-body scanning is NOT IMPLEMENTED (see TODOs).
- Redirects: GitHub Pages project sites support NO server-side redirect
  mechanism. Changed/retired URLs are a policy violation anyway (no slug
  changes), so redirects are intentionally absent — see
  `docs/MASTER-FIX-MATRIX.md` (accepted limitation, P3).

### D. Post-build HTML integrity

- The publish path regenerates hubs/sitemap only through
  `factory.mjs --publish` / python generators (byte-equality enforced by
  `--check` in CI on every publish).
- Live HTML must be byte-identical to the repo file (step B.4). Any drift
  means the Pages build is stale or a push was truncated — stop the chain
  and re-verify from local truth.

## Expected results

- Every sitemap URL returns 200 live; zero noindex; drafts 404; live bytes
  == repo bytes; sitemap count == consistency count; robots.txt live ==
  repo file.

## PASS/FAIL criteria

- PASS: all of A (consistency OK, both `--check`s clean, suites green)
  AND all of B (no non-200 sitemap URL, no noindex, no leaked draft,
  byte-integrity, count agreement).
- FAIL: any leaked unpublished URL (P0 — blocks publish chain), any
  canonical/sitemap mismatch (P0), any 404 in the sitemap (P1), stale
  robots.txt (P1), byte drift (P1 — suspect truncation, re-push).

## Error handling

- 404 on a PUBLISHED URL: check the Pages deploy finished; verify the file
  exists in repo at `output_path`; re-run `--consistency`; if the publish
  transaction was interrupted → `--recover`.
- Draft reachable live (404 expected but 200): STOP immediately — this is
  a P0 deploy-gate breach; verify the file is really under `_drafts/` and
  that no direct `output_path` copy was pushed.
- Sitemap count drift: regenerate via the operator `publish`/
  `consistency` flows only; never hand-edit `sitemap.xml`.

## Checkpoint

- Evidence: save the exact curl outputs (status codes, md5 pairs, counts)
  into the chunk report. Claims without evidence = NOT VERIFIED.
- Re-run level: full live sweep after every publish; source sweep is part
  of every QA/CI run.

## Rollback

- Technical fixes are forward-only on published pages. A bad commit is
  reverted by pushing the previous file content (verified possible via
  the GitHub file-push API) — never by deleting URLs.
- Sitemap/hub corruption: `--recover` then the operator `consistency` op
  or `node scripts/js/factory.mjs --consistency` (read-only verify) and a
  regenerating publish if the ledger itself must be corrected.

## Known limits / TODO (do NOT claim as verified)

- TODO: automated site-wide broken-link crawler (current method: sample +
  hub sweep).
- TODO: site-wide near-duplicate body scan beyond the per-article gate.
- NOT IMPLEMENTED: server-side redirects (platform limitation, documented).
- robots.txt on this GitHub Pages PROJECT site applies to the whole host
  `thuexemayhanoi.github.io` path space owned by this account — it cannot
  grant or restrict anything outside `/shop/` on foreign hosts. No
  per-directory robots isolation exists.
- Live checks verify status/bytes only; rendering-level SEO (what Google
  sees after JS execution) is NOT VERIFIED without a rendering tool.
